## 1. Recommendation

**Proceed to workplan authoring, with substantial tightening before commitment.** Preserve the product goal: one portable native ClauseScript asset, an irregular application hierarchy, funded fleet birth, paid movement, finite hostile damage, durable continuation, and measurements from that same ordinary resident Studio session. Preserve the Owner's sequencing: characterize the application before releasing new kernel optimizations. Movement and combat remain required; the strategic response probe remains optional.

The proposal is strongest where it distinguishes economic authority, product acceptance, and measurement. It already rejects fake fleet spawns, compiler-shaped economics, UI-owned state, double-bounded transit, duplicated HP debt, and performance claims obtained by changing the workload. Those provisions should survive into the committed document.

Its main risk is **underestimating the gap between a landed generic substrate and a complete authored application**. Several current Studio and authoring paths are narrower than the product being promised. Calling later work “bindings” will not make those gaps routine. Conversely, giving every binding its own DA contract relay would reproduce the last track's cadence.

My recommended shape is:

1. Resolve a compact set of authority decisions and truthful capability classifications at opening.
2. Establish the clearance classes and companion-file rules that implement the desired graduation policy.
3. Build vertical product increments, each completing the lifecycle it introduces.
4. Keep the inherited measurement obligations explicit and finite.
5. Make UI replacement a measured decision with a separately bounded implementation sequence.
6. Release kernel candidates only after the complete application's baseline and the required Owner decision.

Four matters need explicit DA treatment: canonical source-to-session fidelity; multi-input construction and placement; paid transition and combat effect ordering; and the actual graduation machinery. The rest should be made as mechanical as the admitted contracts allow.

## 2. Findings that materially change the workplan

### F1 — The Studio bridge currently substitutes a small RF profile for general authored economics

**Severity: blocking for the first faithful product slice. Proposal §§2, 4, 7 Phase 1.**

This is a confirmed code limitation, beyond the proposal's general instruction to audit fidelity.

In `compose_recursive_rf_profile`, the current bridge:

- selects the first owner with three positive-surplus participant candidates;
- takes exactly three candidates;
- clears the authority tree's property maps;
- creates a Studio-specific RF property and root budget;
- populates the selected owner and children with that profile.

The alternate route retains the hydrated root. Separately, `field_bearing_game_mode` clears events, capability trees, region fields, and domain packs, then selectively rebuilds supported field overlays. These are explicit restrictions in the current implementation. Ordinary GPU execution of the resulting profile does not establish that arbitrary authored economics reached the GPU unchanged. [Studio bridge](https://github.com/khorum08/SimThing/blob/435aab7e9b77515d6107172ff7eed363a9e15809/crates/simthing-mapeditor/src/studio_live_session_bridge.rs).

The projection also requires the first embedded static galaxy lattice for its rebind route. Its authority-tree candidate initially contains empty placements and links. The proposed portable asset therefore needs a concrete topology/dependency contract; “self-contained preferred” cannot stand in for one. This does not prove all projection modes are wrong. It identifies the present route's envelope. [Projection](https://github.com/khorum08/SimThing/blob/435aab7e9b77515d6107172ff7eed363a9e15809/crates/simthing-clausething/src/clause_scenario_projection.rs).

**Workplan change:** make installed semantic fidelity the first vertical exit. Name which existing admitted representation owns each property, program, topology edge, owner relation, and observation binding. Decide whether the canonical interchange carries executable declarations itself or identifies the portable execution bundle that accompanies it. Do not invent a second IR to conceal the split.

**Discriminating witness:** use two owners, more than three participating children, unequal depth, zero-valued but present participants, and distinct authored policies. Compare source intent with the admitted installed tree and born outputs through both native loading and supported interchange. Change an unselected child's contribution and the second owner's policy; both must affect the appropriate installed economics. An unsupported executable declaration must fail before activation, with source provenance.

Keep historical stage-only and negative contracts intact. Convergence means eliminating unauthorized semantic substitution, not falsely declaring every old fixture fully executable.

### F2 — Multi-resource construction is a real admission decision, not an assumed Vector CostBand capability

**Severity: blocking for fleet birth. Proposal §§3.2, 3.5, 7 Phase 2.**

Current `ActionBandRequirementSemantics` exposes `AtomicCommonDepthCommitment` and `PersistentScarceGrantHolding`, but the admission loop calls `reject_deferred_requirement` and rejects both. Scalar CostBand exists. The old “pre-8.x” name on the error does not prove that the intended multi-lane capability landed later. [Authored forms](https://github.com/khorum08/SimThing/blob/435aab7e9b77515d6107172ff7eed363a9e15809/crates/simthing-spec/src/spec/action_band.rs), [admission rejection](https://github.com/khorum08/SimThing/blob/435aab7e9b77515d6107172ff7eed363a9e15809/crates/simthing-spec/src/compile/action_band_admission.rs), [scalar CostBand](https://github.com/khorum08/SimThing/blob/435aab7e9b77515d6107172ff7eed363a9e15809/crates/simthing-core/src/cost_band.rs).

This establishes a gap in that ActionBand door. It is not proof that no composition of ordinary settled stocks can implement the required recipe.

**Choose and prove one construction model:**

| Model | What has to be true | Engineering consequence |
|---|---|---|
| Settled inputs held as ordinary work-in-progress inventory | Delivered inputs become explicitly owned stock in ordinary SimThings/lanes; they remain recoverable until the recipe consumes them. Storage, cancellation, capacity, and placement dispositions are admitted. | Prefer this if existing generic ownership and consumption doors suffice. It may avoid opening provisional cross-market holding. |
| Atomic multi-lane recipe completion | A generic admitted commitment consumes the required resource vector and authorizes completion under one declared lifecycle. Independent lane grants cannot impersonate the atomic decision. | Requires an explicit capability amendment if the necessary authority is absent. Complete contention, refusal, cancellation, release, and restart semantics with its first consumer. |

Neither model may convert incomplete inputs into irreversible “build credit” merely to hide missing atomicity. Neither may create a construction-specific allocator.

A useful falsifier is two projects competing for one unit of each of two inputs, with separate allocation outcomes favoring opposite projects. The model must explain ownership, progress, cancellation, and why the declared product profile can eventually complete. Conservation alone permits a permanently stranded economy.

**Placement is part of this decision.** State when a residency commitment is acquired, when materials are consumed, and what happens if placement becomes unavailable. A touched generation fault remains fail-stop; it cannot be repaired by an invented rollback.

The structural door already admits `AddChild`, `Remove`, and `Reparent`. Reuse it. Prove that repeated completions mint fresh instances and bind their properties, overlays, membership, observations, and child structure. A frozen request template and a completion counter do not alone prove repeated fleet assembly. [Structural authorization](https://github.com/khorum08/SimThing/blob/435aab7e9b77515d6107172ff7eed363a9e15809/crates/simthing-driver/src/action_band_consequence.rs).

### F3 — Partially paid movement needs a binding to the specific local transition

**Severity: contract decision before movement implementation. Proposal §3.6.**

The proposal correctly separates local work from changing whole-route potential. It does not yet say enough about the identity of the transition to which paid work belongs.

Suppose a fleet has paid two of three work units toward neighbor A. The destination, topology, or PALMA descent then changes to neighbor B. A scalar “two units of progress” is insufficient to decide whether that work remains valid. Silently applying it to B creates transferable progress that the model never authorized.

Bind partial work to the admitted subject, target revision, topology revision, and authorized adjacent transition, using existing ordinary state and boundary identities. Define whether the remaining local price is frozen for that transition or repriced prospectively. Define retarget, cancellation, edge removal, blockage, source death, and placement-refusal dispositions. This is bounded local transition state; it does not require a route sequence or a movement-owned planner.

Also settle these details:

- A finite PALMA sweep is not a global shortest-path guarantee. Freeze the reachable envelope and stall/refusal behavior.
- Equal lawful descents need an admitted deterministic selection rule or an explicit refusal. Physical storage order must not decide.
- Consume the signed native flux in the authorized direction. `abs(flux)` would turn opposed transport into fictitious mutual progress.
- Use exactly one declared native conserved-progress bound. The current vocabulary already distinguishes RF grant, Gu-Yang available, and Gu-Yang realized authority.
- Treat transit capacity, stored movement work, CostBand remainder, partial local progress, and RF unresolved demand as different quantities.
- Record the number of distinct destination fields, their horizons, and active bindings. One newly seeded field per fleet can dominate costs even when total entity count looks modest.

The example costing 3 then 4 work units with production of 2 per generation is useful. Add a checkpoint after partial payment, then change the edge cost or target. The continuation must account for every work unit and preserve the one-local-step boundary rule.

The field laws remain those of the current Core: STEAD signal, PALMA min-plus potential, and conservative non-gradient Gu-Yang relaxation through the common admitted FieldSweep machinery. Historical descriptions that reduce Gu-Yang to saturation alone must not replace the current law. [Core](https://github.com/khorum08/SimThing/blob/435aab7e9b77515d6107172ff7eed363a9e15809/docs/simthing_core_design.md), [ActionBand composition and native authority](https://github.com/khorum08/SimThing/blob/435aab7e9b77515d6107172ff7eed363a9e15809/docs/multi-axis-ActionBand-STEAD.md).

### F4 — Combat needs one explicit generation order and two-sided accounting

**Severity: contract decision before combat implementation. Proposal §3.7.**

The simultaneous-Current proposal is reasonable. Its HP formula does not settle damage caps, repair admission, repair spending, and casualty timing by itself.

For example, with Current HP 5, emitted damage 10, and funded repair 5:

- capping applied damage at Current HP before repair can leave 5 HP;
- applying net damage before a final clamp can leave 0 HP;
- testing the terminal crossing before repair can remove the target despite later positive HP.

These are different authored combat models. The implementation must not choose accidentally.

**Require a small generation-order table** naming eligibility from Current, funded output, allocation/delivery, receiver deformation, damage and repair caps, the single HP write through admitted actuation, and the terminal crossing. State which repair can avert death and the disposition of unusable repair inputs. Treat this as admitted content/effect ordering unless the audit exposes a generic gap.

Damage has both source and target constraints. Every source has finite output; each eligible target has a depletion bound. Per-target aggregation alone does not prevent a source's output being cloned across several targets. Independently distributing each source and then clipping every target can also strand capacity or change attribution. Name the ordinary market/transfer composition that owns these constraints and its exact or continuous quantity contract. No second combat settlement pass is implied.

Keep `f(U)=0` for the proposed generation-local HP service claim, if such a claim is needed. Remaining HP is already the next generation's work. Keep zero-quantity members distinct from departed streams. Apply mitigation once and retain the separate accounting units of operating energy, emitted damage, and HP depletion.

**Minimum useful witness:** multiple attackers and multiple targets; one target receives overkill while another remains eligible; a simultaneous mutual kill; funded repair at a terminal boundary; departure/reentry; physical permutation; and checkpoint continuation. Distinguish emitted, delivered, applied, and expired quantities. This is one composed lifecycle proof family, not a request for a new generic combat invariant.

### F5 — The natural hierarchy still needs an explicit mapping to three different relations

**Severity: opening model decision. Proposal §§3.2–3.3, 3.5.**

Write down separately:

1. spatial containment and structural residency;
2. RF parent/scope relationships and admitted transport couplings;
3. faction ownership and policy attachment.

An irregular galaxy tree does not determine all three. In particular, do not make owner seats spatial containers for convenience; the current Studio bridge's owner-centered demonstration profile is not the proposed application model.

The opening authored model should identify concrete sites and uneven paths, the market scopes that contend, the physical connections that carry logistics and movement, and the relations that authorize hostile effects. Use a small explicit specimen before scaling parameters. “At least three parent-child edges” is too weak to establish meaningful depth, cross-scope service, or a spatial bottleneck.

Also freeze a viable initial economic state: source rates or exhaustible stocks, conversion coefficients, bootstrap fuel/energy, upkeep, and enough productive surplus for the declared fleet-completion horizon. Test a genuine shortage and recovery without quietly replenishing stock outside admitted inputs. A replenishment source is acceptable when it is authored and accounted for.

Make the simulation-time convention explicit. Production, upkeep, propulsion, and weapons use the admitted generation/time contract. Studio speed changes wall-clock scheduling; it must not silently multiply recipes or alter economic outcomes for the same generation-stamped inputs.

### F6 — Required characterization and deferred optimization are not yet cleanly separable at closeout

**Severity: workplan sequencing and completion definition. Proposal §§6–7.**

The text requires a conclusion on every research family while deferring new optimization until the full application has been reviewed. Several table cells combine present-path measurement with experiments that require a new candidate implementation. A workplan must distinguish those obligations precisely.

Use separate status fields for:

- instrument validity;
- current-path characterization;
- historical comparison where the reference is still meaningful;
- candidate release;
- candidate execution and result;
- inherited budget/debt disposition.

“Measured constraint; optimization deferred” can complete characterization. It cannot count as an executed candidate comparison or a discharged performance debt. The proposal says this in prose; the committed rows and closeout predicate must express it without ambiguity.

**Retain the inherited first-rung Gu-Yang precondition.** The lease explicitly calls for remeasurement at performance-track opening. Author the measurement contract before dispatching that rung, restore a faithful contained measurement route, and distinguish that work from releasing a production optimization. Do not move or erase the precondition merely to speed up the visible slice. [Performance leases](https://github.com/khorum08/SimThing/blob/435aab7e9b77515d6107172ff7eed363a9e15809/scripts/ci/closeout_artifacts.tsv).

Retain the proposal's inherited tiled-gather comparison limits of at most 1.25× median and 1.5× worst ratio against the comparable retained reference, or obtain an explicit adjudication of a changed reference/envelope. Instrument repair, a missing measurement, and an unmet ratio must have distinct dispositions.

At the same time, the entire research campaign need not gate the first application increment. The opening rung should discharge its actual prerequisites and establish instruments. Subsequent measurements should land at their first truthful consumers. The full growing movement/combat scenario remains the decisive application baseline.

Maintain the frozen Phase-14 comparator and a separate current composite T_R. For independent trees, define per-tree causal intervals and application throughput/freshness without introducing a global runtime synchronization point just to make measurement convenient.

### F8 — Reliability must be part of each capability's first consumer

**Severity: rung-boundary correction. Proposal §§4, 7 Phases 2 and 4.**

The proposal appropriately says persistence probes start early. Make that enforceable in each row. Fleet birth must already handle capacity refusal and membership; movement must already handle retarget and partial-work continuation; combat must already handle removal and stream termination. Later reliability rungs deepen cross-products and soak duration.

Checkpoint at a lawful generation boundary that still contains unfinished work: held recipe inputs, partial transit, active attack intent, nonzero unresolved demand, and recently changed membership. Restore into the same realm with a new incarnation, fork into a new realm, and compare canonical economic continuation under those identity laws.

For new instances, distinguish pre-admitted template/storage capacity from pre-created fleets. Paying finite instance capacity up front is lawful; pretending those slots are completed product output is not. Growth must either consume admitted capacity, use a lawful rebind/growth door, or refuse explicitly. Define the product envelope before its limits are reached.

### F9 — Observation needs a coherent causal view without becoming a full-history requirement

**Severity: acceptance and performance detail. Proposal §5.**

An executing generation and an observation generation are necessary but not sufficient for a coherent multi-panel display. A selected fleet's HP, funding, location, and casualty marker should identify the same observation bundle or explicitly reveal that their generations differ.

Use bounded, subscription-scoped observations. Distinguish coalescible presentation samples from required replay/structural products: losing a graph sample and losing a casualty or economic authorization are different events. Preserve the typed exhaustion contract for required egress.

For diagnosis, expose a compact causal chain from authored declaration to installed binding to born value and resulting boundary event. This can reuse existing provenance and identity; it should not create another economic registry. It will make both compiler fidelity review and the eventual Studio UI migration much cheaper.

### F10 — The performance matrix needs a finite, actionable execution schedule

**Severity: planning completeness. Proposal §6.3.**

“Full declared manifest” becomes credible only when the committed manifest enumerates actual runs, required hardware, owners, and stop conditions. Retain the proposed bounded combinations and focused cross-products. Do not silently expand them into every Cartesian combination.

Add cardinalities that the proposed application is especially likely to expose: distinct destinations and admitted field channels; target eligibility edges; recipe lanes; pending structural products; retained work-in-progress; active versus reserved instance rows; selection/subscription count; and separately measured simulation/presentation GPU memory.

For each scale curve, report the first failure or service-level crossing and its cause. A typed admission limit, rising generation cost, starving recipe, stale observation queue, and OS/GPU memory failure are different constraints.

Use a fixed-generation comparison for semantic equivalence and per-generation performance, plus a wall-clock interactive run for responsiveness. Otherwise a faster version can produce more fleets and more work during the measurement interval, making an honest improvement appear slower.

Keep the full economy→birth→movement→combat→release→replacement workload and a live carry/cap/membership/rebind/restore composition. Add focused counterexamples only where they discriminate a real missing contract.

## 4. Studio: whether to replace egui, with what, and at what cost

**Recommendation: run a bounded native-UI prototype early; decide before implementing the large new economy/movement/combat inspector surface. Do not make an unmeasured full rewrite a prerequisite for the first faithful Studio slice.**

The maintainability and styling argument is stronger than the currently unmeasured performance argument. Either toolkit can be slow if the client rebuilds models, over-subscribes observations, or performs expensive work on every frame. Native UI also incurs layout, text, change-detection, and rendering costs.

### 4.1 Grounded migration scope

The current lockfile has Bevy 0.16.1, bevy_egui 0.36.0, and egui 0.32.3. Native bevy_ui is already present. The central `app/ui.rs` is 3,096 lines with 229 egui references. It mixes painting with temporary-context command flags and asynchronous clause-loader integration. Window dragging, frosted bounds, settings, diagnostics, selection, and lifecycle actions all matter.

There are useful existing seams: the simulation-clock UI model, scenario-library UI model, and runtime save/load UI model have no egui references in the inspected files. Preserve and improve those seams instead of creating a parallel application model. [Studio UI](https://github.com/khorum08/SimThing/blob/435aab7e9b77515d6107172ff7eed363a9e15809/crates/simthing-mapeditor/src/app/ui.rs), [mapeditor manifest](https://github.com/khorum08/SimThing/blob/435aab7e9b77515d6107172ff7eed363a9e15809/crates/simthing-mapeditor/Cargo.toml), [lockfile](https://github.com/khorum08/SimThing/blob/435aab7e9b77515d6107172ff7eed363a9e15809/Cargo.lock).

The code already times the egui pass and can hide the main panels. Use those controls to isolate costs, while verifying what dialogs and observation work remain active. A “hidden” run is a diagnostic condition, not the accepted full UI workload.

### 4.2 Candidate choice

| Choice | Fit for the requested direction | Main tradeoff |
|---|---|---|
| Keep egui, improve application/view separation | Lowest disruption; usable baseline and incremental product delivery | Does not provide CSS-authored native Bevy UI |
| Native bevy_ui with a CSS layer such as bevy_flair | Closest match to stylesheet-driven styling within the existing Bevy client | Styling does not supply the entire editor interaction layer |
| Upgrade Bevy and evaluate Feathers widgets | Potentially useful editor/inspector building blocks | Introduces a dependency migration and an experimental widget surface |

Flair supplies CSS-like styling, inheritance, selectors, and hot reload over Bevy UI; it does not dictate UI construction or implement missing Bevy widgets. Its compatibility table lists Flair 0.4 for Bevy 0.16 and Flair 0.8 for Bevy 0.19. Verify the older release's actual feature set in the prototype; do not assume every current README feature exists in 0.4. [Flair](https://github.com/eckz/bevy_flair).

Feathers is Bevy's themed editor/inspector widget collection. Its current documentation explicitly calls it experimental and unfinished. Treat widget behavior, theme ownership, and upgrade stability as prototype questions. Combining it with an independent CSS layer also requires deciding which styling system owns each property. [Feathers](https://docs.rs/bevy/latest/bevy/feathers/index.html).

A Bevy upgrade affects more than egui: SimThing's tools crate also uses Bevy, and Studio has custom render/material/text integration. Bevy's 0.16→0.17 migration alone includes render, text, UI, event, window, and wgpu changes. The current lockfile already contains separate wgpu versions; an upgrade is not automatically a renderer or simulation-backend unification. [Tools manifest](https://github.com/khorum08/SimThing/blob/435aab7e9b77515d6107172ff7eed363a9e15809/crates/simthing-tools/Cargo.toml), [official migration guide](https://bevy.org/learn/migration-guides/0-16-to-0-17/).

### 4.3 Prototype and decision evidence

Use one existing settings/inspector pane plus live observation, rather than a static button showcase. Cover a numeric input, scrolling list, selection, modal focus, keyboard navigation, clipboard/text entry, pointer capture over the map, and window/DPI behavior on the reference Windows machine. Verify source diagnostics and generation-stamped readouts.

Extract commands currently stored in egui context memory into the existing application command/state owner. Both the prototype and existing UI must reach the same session operations and observation model. Transitional coexistence needs explicit input ownership and a deletion endpoint.

Compare paused and running workloads, first display, steady visible panels, active editing, resize, and long lists. Measure full-frame tails, UI CPU cost, render/GPU cost where available, input latency, memory, and observation freshness. Hold generation-stamped commands and observation subscriptions constant for economic comparison.

Choose the native stack if it demonstrates the required behavior and a credible maintenance/styling benefit within budget. A performance-neutral result can still justify a product decision; describe it honestly. If widgets or rendering integration require disproportionate custom work, finish 0.0.8.8 on egui with the improved application seam.

### 4.4 Effort estimate

These are **person-days for one engineer experienced with Rust/Bevy**, based on static inspection. They are not promised elapsed time, AI-agent turn counts, or measured project velocity. New economic engine capabilities are excluded.

| Work package | Initial range | What is included |
|---|---:|---|
| Prototype and version/widget decision | 2–4 days | Representative pane, integration probe, baseline comparison, explicit feature gaps |
| Application commands and native shell | 4–7 days | Existing-state reuse, focus/input ownership, shell/layout, loading and error interaction |
| Existing panel and workflow parity | 7–12 days | Settings, picker, inspections, telemetry, dialogs, save/load commands, selection |
| Integration hardening and egui retirement | 5–9 days | Windows/DPI, map picking, text/render interactions, tails, long sessions, cleanup |
| **Migration on a compatible Bevy version** | **18–32 days** | Sum of the above; budget roughly **4–8 engineering weeks** including contingency |
| Optional Bevy/toolchain/render upgrade | **+5–15 days** | Dependency migration and the affected render/text/UI regression work; revise after the spike |

At an actual loaded daily cost of `r`, the labor planning envelope is `18r–32r`, plus `5r–15r` if the upgrade is chosen. No monetary rate is assumed.

The greatest uncertainty is editor interaction parity, not CSS translation. A custom code editor, rich docking system, or additional product UI scope would exceed this estimate. Several agents do not divide the schedule linearly because the application model, input routing, and renderer remain shared integration surfaces.

Retain the E8 qualification procedure when its sealed semantic bundle or required adapter/compiler/runtime tuple changes. Do not roll the numeric pin solely because an unrelated UI source file changed.

## 5. How to obtain more Orchestrator-graduatable rungs

**Flatten decisions into admitted contracts; keep implementation increments bounded.** One active production rung remains the default. The user-facing deliverable of each increment can span authoring, loading, execution, and observation if its ownership and evidence are already settled.

### 5.1 Establish the routing policy at opening

The opening DA-reviewed governance change should:

1. Define an explicit graduation authority independently of coder assignment.
2. Register narrowly scoped classes for admitted ingress mapping, scenario content, Studio presentation, measurement instruments/results, and named lifecycle integrations where their laws are settled.
3. Include predictable companion surfaces: exports, owning tests, documentation, evidence, permitted lifecycle rows, approved asset paths, and approved manifest/lockfile changes.
